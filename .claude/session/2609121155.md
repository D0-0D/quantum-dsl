## 起因
用户对上午的 `docs/design/component-library.md`(第一稿, 306 行)的判决: 「完全没到要点上, 细节加了一大堆, 基础图像不对」。三点:

## 查实(全部有出处, 写进设计稿 §1)
- **业界端口契约**: qiskit-metal `QComponent.add_pin` 记 points/middle/normal/tangent/width/gap(`base.py:843–880`); `TransmonCross` 的爪 + 引出短线
  由 qubit 画, pin 在短线末端、宽 = `claw_cpw_width`(`transmon_cross.py:234–280`); `QRoute.trace_width` 是路由自己的选项, 不继承 pin、不检查(`qroute.py:85,143,261–293`)。
  KQC `Element.add_port(name,pos,direction)` + "corner" 参考点; Swissmon 持有 `cpl_*` 与 `port_width`; `WaveguideComposite.length_before` 插蛇形定长。
  → 用户直觉与两大工具一致; 我们比 qiskit-metal 多做「宽度继承 + 不匹配 raise/taper」。
- **等效长度物理**: λ/4 开路端挂 C: tan(βl) = 1/(ωZ0C) → Δl = arctan(ωZ0C)/β ≈ C/C′; λ/2 同式。Göppl 2008 JAP 104, 113904 Eq.(12)(15)(18)
  (pypdf 抽文本核对, scratchpad `ref/goppl.txt`)。量级(`lumped_cpw` 7 GHz, 10/6 CPW, Si 500 µm): C′ = 0.1635 fF/µm; 10 fF → 61 µm → λ/4 1.4% ≈ 100 MHz。
  flip-chip d = 5 µm 下读出爪平行板下界 ≈16 fF → 必须记账。
- **gmsh `.geo` 边界**: 手册 §5.1.7 宏无参数、变量全局; §1.5 复杂几何请用 API。本仓踩坑(Call 独占行、宏只能住 include 库、嵌套覆盖、flex 崩)全是其后果。
- **换引擎接口面**: `geo_model(path)` 三个消费者只读 2D Physical 组(`geo.py:75`/`gds.py:45`/`mesh.py:85`) → 接 callable 即可, 下游零改动。
  探针(scratchpad `probe/`): Python 函数模板画圆盘双岛 + 共形爪, 打三段 Physical; `gmsh.write("*.geo_unrolled")` 在 OCC 下写成 `Merge "*.xao"`,
  `.brep`/`.step` 也能出, Physical 名往返无损 → GUI 可看。
- **fork gmsh 可行性**: subagent 实证(gmsh master 5.0.0-dev, 报告 scratchpad `gmshfork/REPORT.md`): Gmsh.y 7 882 行 bison 直译无 AST, 宏 = fgetpos/fsetpos
  跳转, 符号表三张全局 map; 语句级带参 + 局部作用域 3–4 人周, 表达式级返回值做不出(与列表下标语法冲突); 官方 wheel 是 CI 自编静态 OCCT 打包,
  fork = 永久私有构建链; 手册把「无私有变量、宏无参数」列为已知局限并指向 API; API 无能力缺口且消灭「Macro 进程级永久状态」坑。→ **不 fork**。

## 关键决策
- 库的封装单位 = 模板(整只 qubit), 不是 `.geo` 宏; 实例化在 YAML 版图, 编译器同时产几何与 `circuit_model`/`subsystems`。
- 几何引擎 = gmsh Python API; 不 fork gmsh; 不发射 `.geo` 文本; 手写 `.geo` 保留为底层输入; `qlib.geo` 冻结。
- CPW: 无坐标输入, 只接端口; 宽继承端口; 爪归 qubit 模板画、电学归谐振器 net; 模板给 `equiv_length_um`, 定长时 L_drawn = L_target − Σleq。
- worktree `cpw-meander`: 只合并 `gds.py` 曲率 16 行; 路由宏与例子不以 `.geo` 合并, 算法与三条测试搬 Python。

## 第二轮: v2 被否 → 框架稿 v3
用户判决 v2: 「库的实现和原来的用法完全割裂」; 设计一节细节太多, 先提可行想法; 核心问题是 API 几何与手写 `.geo` 怎么进同一张图,
qubit 模板跨 layer 时想在某 layer 再用 `.geo` 补几条线怎么办; `qlib.geo` 不是软件的一部分, 是用户正常用 `.geo` 的产物, 不是要搬运的东西;
框架没弄明白前别写搬运与测试细节。

探针(scratchpad `probe2/`)钉死混用机制:
- `.geo` 能 merge 进已有 API 几何的模型, 对 API 面做布尔; 解析器变量双向(`setNumber/setString` → `.geo`; `.geo` 赋值 → `getNumber`);
  局部坐标 `.geo` 片段 merge 后按差集 `rotate/translate`; `.geo` 可当模板(输入变量 + `StrCat` 拼名 + `out_*` 输出, 两次实例化正确)。
- 坑: 全名重复 API 侧**静默**空名(`.geo` 侧 raise); `removePhysicalGroups` 后同名重挂不可靠; `.xao` 导入的组会被后续 `.geo` `Physical` 语句抹掉。
  → 编排器只累积不删组、统一校验重名、`.xao` 只作导出。
- API 先挂组再 merge 带 `Physical` 的 `.geo`: 全部保留。

`docs/design/component-library.md` 重写为 **框架稿 v3**(~170 行): 一个 gmsh 模型是汇合点; 三条过界通道; 模板两种写法(Python / `.geo`)同构;
版图 = 有序步骤(template / geo / route), 今天的 `geo:` 是只有一步的退化情形; 端口/CPW 框架级规则; 与现状关系(手写 `.geo` 不变不搬不冻结,
qlib 是用户文件); 开放问题 5 条; Chen 映射 5 行; 查实四段。删掉了 v2 的 L1–L8、五步落地、搬运与测试细节。

用户追问: 「有考虑过 yaml+geo 整体作为一个模板吗, 现在模板完全是 Python 调 API, 不一定很好」→ 采纳为默认形态:
